# Demystifying Agent Skills：它们为什么有效——又为什么失效

**论文：** *Demystifying Agent Skills: Why They Work — Until They Don't*  
**作者：** Zhiyuan Jiang, Fangrui Huang, Hanwen Xing, Xander Wu, Yipeng Gao, Rui Cao, Mengdi Wang, Shilong Liu, Yijiang Li  
**机构：** Princeton University, UC San Diego, Stanford University, USC, Johns Hopkins University  
**arXiv：** [2608.14036](https://arxiv.org/abs/2608.14036) · [PDF](https://arxiv.org/pdf/2608.14036)  
**发布时间：** 2026 年 8 月

---

## 背景：一个被忽视的基础问题

当前的大语言模型（LLM）Agent 系统越来越依赖"经验复用"——把之前任务中的执行轨迹、调试过程、环境配置步骤等保存下来，供后续任务调用。在这些记忆形式中，**Skill（技能）** 是一种特别受关注的抽象：它不像原始执行日志那样冗长，而是被提炼成一份结构化的操作指南，描述"做什么、检查什么、避开什么坑"。

现有的研究已经反复验证了一件事：给 Agent 加载 Skill，任务成功率会上升。但这个结论只回答了"有没有用"，没回答更底层的问题：

- Skill 到底在什么环节改变了 Agent 的行为？
- 同样的经验，写成 Skill 和直接塞给 Agent 有什么区别？
- Skill 失效的时候，问题出在检索、理解，还是执行？

这篇工作的核心目标，就是把 Skill 的作用机制从"黑盒成功率"里拆出来，逐段观察它在哪里帮忙、在哪里掉链子。

## 核心做法：一个对比式的实验框架

作者设计了一套**控制变量实验**，核心思路是：固定底层经验不变，只改变它的呈现方式，然后看 Agent 的行为差异。

### 三种实验条件

对同一个任务，设置三条平行臂：

- **Raw（无经验基线）**：Agent 从零开始，不加载任何先验轨迹。
- **Workflow Memory（原始工作流记忆）**：把之前成功或失败的执行轨迹清洗后，直接作为上下文注入。它保留了完整的操作细节，但也保留了探索过程中的噪音、失败分支和冗长输出。
- **Skill（结构化技能）**：从同样的轨迹池中提炼出一份标准化的 `SKILL.md`，只保留可复用的步骤、检查点和常见陷阱，去掉无关的探索记录。

通过对比这三条臂，就能分离出"Skill 的格式本身"带来的独立效应。

### 四个研究问题（RQ）

**RQ1：表示形式如何影响经验复用？**  
同样的轨迹，写成 Skill 和直接作为 Workflow Memory 注入，Agent 的行为会有什么不同？Skill 的压缩和标准化是否真的能减少噪音干扰？

**RQ2：结果标注（成功/失败信号）有多重要？**  
在提炼 Skill 时，如果去掉"这条轨迹是成功还是失败"的显式标注，只保留纯文本内容，Skill 的效果会不会打折扣？这能区分"经验本身有用"还是"知道哪些做法可行/不可行"更有用。

**RQ3：跨框架迁移是否可行？**  
在一个 Agent 框架（如 Codex）里提炼出的 Skill，放到另一个框架（如 Gemini CLI）里， prompting 风格、工具接口、执行循环全都不一样，Skill 还能不能发挥作用？这检验的是 Skill 的**可迁移性**。

**RQ4：Skill 库的检索瓶颈在哪里？**  
真实场景中 Skill 不是直接喂给 Agent 的，而是从一个库里检索出来的。当库从 5 个 Skill 膨胀到 100 个，且里面混入了语义相近的干扰项（distractor）时，检索精度和最终任务成功率分别怎么变化？

## 核心发现一：Skill 的主要作用是"过程锚定"，而非"知识注入"

这是整篇论文最关键的结论。作者对 8,135 条实验记录做了归一化处理，从中采样 240 条轨迹做开放编码（open coding），最终归纳出 12 种 Skill 使用模式，归入 3 个高层类别，并由人工标注员独立验证（Cohen's κ = 0.952，一致性极高）。

统计结果显示：

- **65.7%** 的 Skill 有效案例，归因于 **Procedural Anchoring（过程锚定）**。
- **4.5%** 归因于 **Explicit Knowledge Injection（显式知识注入）**。
- 其余分布在失败警告、无意义使用、反作用指导等模式。

**Procedural Anchoring** 的含义是：Skill 并没有教给 Agent 什么它不知道的新事实，而是把 Agent 原本就模糊知道该怎么做、但执行时容易手抖的环节，锚定成一套稳定、可复现的操作流程。例如：

- 环境配置的顺序（先装依赖再改配置文件，还是反过来）
- 测试命令的精确参数（加哪个 flag、输出格式要求）
- 验证步骤的 checklist（提交前必须跑哪几项检查）

换句话说，Agent 的失败往往不是"不知道原理"，而是"执行时漏了一步、顺序错了、或者格式没对上"。Skill 的价值在于把这些容易出错的**过程性细节**固化下来，让 Agent 的执行轨迹更稳定。

相比之下，Workflow Memory 虽然也包含这些过程信息，但它同时携带了大量噪音——失败的尝试、多余的探索、冗长的中间输出。这些噪音会增加上下文负担，甚至导致超时或误导。实验数据显示，在匹配对比中，**Skill 比 Workflow Memory 平均高出 6.06 分**。

## 核心发现二：检索精度暴跌，但"选错"未必"做错"

RQ4 的实验结果揭示了一个反直觉的现象。

### 检索精度随库规模急剧下降

当 Skill 池的大小从 5 增长到 100 时：

| Skill 池大小 | 嵌入检索精度 | Agent 显式选择精度 | 实际执行中使用正确 Skill 的比例 |
|------------|-----------|----------------|------------------------|
| 5 | ~89% | ~70% | ~29.6% |
| 10 | ~86% | ~71% | ~22% |
| 20 | ~85% | ~71% | ~15% |
| 50 | ~82% | ~68% | ~7% |
| 100 | ~78% | ~64% | **3.3%** |

可以看到，**实际执行中命中正确 Skill 的比例衰减得非常快**。当库里有 100 个 Skill 时，Agent 在运行时用对的概率只有 3.3%。

### 但任务成功率并没有同比例崩盘

更关键的是：即使 Agent 没有加载到"完全正确"的 Ground-Truth Skill，它有时依然能完成任务。反过来，即使加载了正确的 Skill，任务也可能因为执行层的问题而失败。

这说明 Skill 的作用机制不是"精确匹配→机械复刻"，而是"提供参考性指导→Agent 结合当前上下文自适应执行"。一个语义相近但不完全匹配的 Skill，仍然可能提供足够的过程性提示，帮助 Agent 稳住执行节奏。

这也带来一个设计启示：**Skill 库的管理不能只看"检索命中率"，还要关注 Skill 之间的语义重叠和互补性**——如果两个 Skill 在过程性指导上有大量冗余，那么即使 Agent 选错了，损失也可能有限；但如果 Skill 之间是"看起来很像、实际步骤冲突"的硬负例（hard negative），就容易导致执行混乱。

## 核心发现三：Skills 的三类失效模式

基于轨迹分析，作者把 Skill 失效的情况归纳为三个高层类别（Skill-use Category, SC）：

### SC1：成功执行（Guided Success / Autonomous Success）
Agent 在 Skill 指导下成功完成任务，或完全自主成功。这是理想状态。

### SC2：执行与验证层失败（Execution & Verification Failures）
Skill 本身被正确加载和理解，但在执行过程中出了问题。具体包括：

- **算法逻辑错误**：Skill 描述的步骤逻辑本身有缺陷。
- **静态验证失败**：代码能跑，但输出格式、schema 不匹配。
- **环境基础设施故障**：Docker、依赖服务没启动或配置错误。
- **Shell 命令损坏**：Skill 里的命令被 Agent 错误拼接或转义。
- **背景服务故障**：测试依赖的外部服务不可用。

这类失败与 Skill 的"指导质量"关系不大，更多是执行环境的鲁棒性问题。

### SC3：调用与适用性失败（Invocation & Applicability Failures）
这是与 Skill 机制本身直接相关的失效：

- **超时 / 预算耗尽**：Skill 内容太长，Agent 花在阅读和理解上的 token 过多，导致实际执行时间不够。
- **Skill 指导被误用（Skill Guidance Misapplied）**：Skill 针对的是场景 A，但当前任务是场景 B，Agent 没有识别出差异，机械照搬导致错误。
- **能力边界限制（Capability-Guided Limit）**：Skill 要求 Agent 执行超出其当前能力的操作（例如需要复杂数学推导或特定工具调用能力）。
- **脆弱假设（Brittle Assumptions）**：Skill 隐含假设了某种特定环境状态（如"用户已经安装了 Node.js 18"），但实际环境不满足。
- **上下文不兼容（Incompatible Contexts）**：Skill 在一个框架里提炼，在另一个框架里执行时，工具接口或 prompt 风格不匹配。
- **适应不足（Insufficient Adaptation）**：Agent 把 Skill 当作 rigid checklist，没有根据当前任务的具体需求做灵活调整。

## 跨框架迁移：Skill 比 Workflow Memory 更便携

RQ3 测试了在一个框架（Codex + GPT-5.3-Codex）里生成的经验，迁移到另一个框架（Gemini CLI + Gemini-3.1-Pro-Preview）后的效果。

结果显示：

- **Skill 的跨框架迁移效果显著优于 Workflow Memory**。
- Workflow Memory 因为紧密耦合于源框架的 prompt 风格、工具调用格式和输出习惯，迁移后价值大幅下降。
- Skill 由于已经被提炼成相对通用的过程性描述，对目标框架的具体实现细节依赖更低。

这支持了 Skill 作为"可复用抽象"的设计初衷：它不只是"记住上次怎么做的"，而是"把上次的做法抽象成不依赖具体框架的操作协议"。

## 一个贯穿始终的模式

把几个实验结果放在一起看，可以总结出一个高度一致的画面：

| 维度 | 核心结论 |
|-----|---------|
| **作用机制** | Skill 主要不是注入新知识，而是把已有知识的过程性执行锚定下来（65.7% vs 4.5%） |
| **表示优势** | 同样的经验，提炼成 Skill 比直接塞 Workflow Memory 更有效（+6.06 分） |
| **检索瓶颈** | 库越大，命中正确 Skill 的概率越低（100 个时仅 3.3%），但任务成功率不会同比例崩盘 |
| **失效边界** | 失效通常不是因为"没知识"，而是因为"过程不匹配、假设太脆弱、适应不足" |
| **迁移能力** | Skill 比原始轨迹记忆更易于跨框架复用 |

**一句话概括：Skill 的价值在于把嘈杂的过往经验，蒸馏成稳定、可复用、可迁移的过程锚点；但它的可靠性受限于检索质量、上下文适配能力和执行环境的鲁棒性。**

## 为什么这个工作值得关注

在 Skill 已经被广泛采用的背景下，这篇论文把评估视角从" aggregate success rate（聚合成功率）"推进到了" mechanism-level analysis（机制层分析）"。它提供的不仅是一个"Skill 有用"的实证结果，更是一套**可复用的分析方法论**：

- 通过对比 Raw / Workflow Memory / Skill 三条臂，可以分离"经验内容本身"和"表示形式"的独立效应。
- 通过配对轨迹分析（paired trajectory analysis），可以定位 Skill 在执行的哪一步产生了影响。
- 通过检索隔离实验（embedding ranking、explicit selection、real execution 三条独立臂），可以区分"找不到 Skill"和"找到了但用不好"这两类失败。

对于正在设计 Agent 记忆系统、Skill 库或自进化 Agent 的研究者和工程师来说，这些发现提供了具体的设计指导：Skill 应该优先覆盖**过程性、易出错的执行环节**，而不是堆砌领域知识；Skill 库需要关注**语义区分度**和**冗余管理**；Agent 在执行时需要有**适配和校验机制**，避免机械照搬。
